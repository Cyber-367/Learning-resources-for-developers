**📘 Company Versioning & Release Strategy Documentation**

---

### 🔰 Purpose

This document outlines our standardized approach to versioning, managing releases, tracking changes, and announcing or silently shipping product updates across all our web and mobile platforms.

---

### 🔢 Semantic Versioning (SemVer)

We use Semantic Versioning (SemVer) across all products:

```
MAJOR.MINOR.PATCH
Example: 2.1.4
```

* **MAJOR** – Breaking changes or big public features (e.g., v2.0.0)
* **MINOR** – Backward-compatible features/improvements (e.g., v2.1.0)
* **PATCH** – Bug fixes or small changes (e.g., v2.1.4)

> Every patch or minor update is a building block toward the next major release. They are cumulative.

---

### 🧾 How We Track Versions

#### GitHub + Git Tags

* Code versions are tagged using SemVer format (e.g., `v1.3.2`)
* Tags are created automatically by our CI/CD workflow if the version in code (e.g., `pubspec.yaml`) is new

#### Release Drafting

* We use **Release Drafter** to auto-generate changelogs based on commit history

#### GitHub Releases

* All tagged versions generate a GitHub Release
* Release includes:

  * Changelog
  * Build artifacts (APK, AAB, etc. for Flutter apps)

#### Optional: Confluence/Notion Dashboard

* High-level release table for tracking what's live where

---

### ⚙️ Build Number vs Version

#### Flutter `pubspec.yaml`:

```yaml
version: 1.2.3+10
```

* **1.2.3** → Version (used in marketing, changelogs, release tag)
* **+10** → Build Number (must always increment)

  * Android: versionCode
  * iOS: CFBundleVersion

> Build number is automated via CI (based on GitHub run number or commit count)

---

### 🔁 Announced vs Silent Releases

#### 📣 When to Announce

* New major features or UI redesigns
* Breaking changes
* Big bug/security fixes
* Marketing push
* Required legal/UX notice

#### 🤫 When to Release Silently

* Minor UI tweaks
* Internal refactors
* Analytics/logging
* Backend fixes
* Hotfixes

> All releases are tracked. Not all are announced.

---

### 🚀 Our GitHub Actions Flow (Flutter Example)

1. On push to `main`, CI reads `pubspec.yaml` version
2. Checks if that version tag exists
3. If not:

   * Tags the version (e.g., `v1.3.0`)
   * Builds APK & AAB
   * Auto-generates changelog
   * Uploads artifacts to GitHub Release

---

### 📆 Our Release Cadence

* Patch releases: as needed (bug fixes, hotfixes)
* Minor releases: every 1–2 sprints
* Major releases: every quarter or milestone feature

---

### ✅ Developer Responsibilities

* Bump version in `pubspec.yaml` (or version source)
* Follow Conventional Commits (`feat:`, `fix:`, etc.)
* Test builds locally before merging
* Review changelog before tagging

---

### 📌 Notes

* Tag naming must follow `vX.Y.Z`
* Avoid skipping build numbers
* Never push same version twice
* Rollbacks must increment build number
